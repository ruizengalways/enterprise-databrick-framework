# Enterprise Databricks Framework — Package Blueprint

Status: reusable package foundation; executable pattern runtime implementation in progress.

## 1. Goal

Build an installable Databricks data-engineering framework that a team can adopt inside an existing company platform without copying platform infrastructure or rewriting core ingestion/recovery semantics.

The package converts explicit dataset contracts into validated runtime behavior while keeping source adapters and business/domain transformations replaceable.

## 2. Repository boundary

This repository owns reusable code and semantic contracts only.

It does not own workspaces, Terraform state, Unity Catalog environment topology, service-principal creation, GitHub OIDC configuration, Databricks Bundle environment targets or promotion workflows. Those belong to the consuming organisation or the optional companion `enterprise-databrick-infra` repository.

`enterprise-databrick-customer` is the independent reference consumer used for learning and exact-SHA certification. It owns fixture data and expected outcomes; those do not belong in framework core.

## 3. Core principles

1. Semantics before technology.
2. Capture mechanism is not target semantics.
3. SCD2 is a target contract, not an ingestion mode.
4. Source ordering and ingestion ordering are distinct.
5. Business identity, source-version identity, event identity and delivery identity are distinct.
6. Bronze has an explicit semantic contract: current replica, raw observation append, snapshot history or event history.
7. Every incremental/change workload declares bootstrap, delete completeness, idempotency, retention, reconciliation and recovery.
8. Git/configuration describes desired behavior; Delta/system tables hold runtime state.
9. Reconciliation and repair are first-class runtime capabilities.
10. New vendor behavior extends the package through narrow adapters/providers rather than forks.
11. Platform/IaC choices are injected context, never package ownership.
12. Certification claims are tied to exact framework/customer SHAs and independent expected results.

## 4. Semantic catalogue

The built-in P01-P14 catalogue covers full snapshots, watermark patterns, soft-delete variants, net/full CDC, domain events and snapshot-diff families. Pattern IDs are routing shortcuts; the production contract is the orthogonal metadata dimensions.

The technology-neutral meaning of the catalogue is maintained in `data-engineering-cheetsheet`.

## 5. Runtime package architecture

```text
TableSpec metadata
      |
      +--> Pydantic cross-field validation
      |
      +--> PatternRegistry
              |
              +--> built-in semantic handler
              |
              +--> extension provider (edp.patterns)
                        |
                        +--> validate(spec)
                        +--> build_runtime(spec, context)
```

`RuntimeContext` receives Spark/Lakeflow objects and environment-specific inputs from the consuming project. Core does not discover or provision infrastructure.

## 6. Metadata contract

A dataset specification answers:

- source data semantics
- capture/delivery mechanism
- change granularity
- bootstrap/handoff
- cursor and authoritative ordering
- business/source-version/event/delivery identity
- Bronze contract
- Silver contract
- delete semantics
- quality/quarantine policy
- reconciliation rules/cutoff
- schema evolution
- fidelity/retention
- recovery and SLA

Invalid combinations fail before deployment where possible.

## 7. Recovery and operability

Package runtime/control semantics support retry safety, replay from trusted Bronze/source history, snapshot reload/full rebuild, source-state tracking, reconciliation outcomes, repair requests/runs, schema-change events and incidents.

Code rollback and data recovery remain separate operations.

## 8. Extension boundary

A new source technology should first reuse an existing semantic pattern and provide only capture/source adaptation. A truly new semantic pattern is delivered as an extension package registered through `edp.patterns`.

Business transformations are explicit code in the consuming domain project; core must not know order/customer/SAP-specific column selections unless they are part of a generic semantic contract.

## 9. Testing and certification

Package tests include:

- metadata schema/cross-field tests
- pattern contract tests
- deterministic transform tests
- ordering/redelivery tests
- SCD2 invariants
- schema evolution compatibility
- reconciliation/recovery tests
- extension registration tests

`enterprise-databrick-customer` adds independent consuming-project evidence:

- deterministic source fixtures;
- expected business outcomes not generated by framework code;
- exact framework SHA lock;
- failure-injection scenarios;
- local package-integration evidence;
- real Databricks runtime/recovery evidence when those certification stages are executed.

Package CI success alone must never be described as full Databricks runtime certification.

## 10. Distribution

The primary deliverable is a versioned wheel. Consuming projects should pin a released version/SHA-derived artifact rather than copying `src/edp_framework`.

Package CI validates examples, lint, strict typing, tests and wheel build. It intentionally performs no Terraform apply or DEV/UAT/PROD deployment.

## 11. Companion infrastructure

`enterprise-databrick-infra` provides optional Terraform modules and platform templates. The package has no mandatory dependency on that repository.

This split reflects normal enterprise ownership: platform engineers maintain infrastructure; data engineers consume a stable framework API and onboard datasets without editing Terraform.
